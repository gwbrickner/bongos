No S1/S3 bugs. Finding 6 is open because it has no fix that a test can check. With IF=1 at the call, the bug needs an
interrupt to land inside the critical section, which one CPU cannot do on demand. With IF=0 at the call, nothing can
clear Remote IRR, so a fix means an API change (for example a BUSY status) or a design note in D-174. Suggested fix
when level pins get their first user (PCI INTx), or in M3.5: when the caller had IF=1, poll with an interrupt
window (`archIrqRestore`/`archIrqSave` around each `archPause`). Also say in `irq.h` that unrouting a pending level
pin at IF=0 stalls for the full bound. No driver routes a level pin yet, so this is S4.

Suspicions checked and dropped:
- x2APIC by reading against SDM Vol 3A §10.12 (QEMU 8.2 TCG refuses it: `-cpu max,+x2apic` prints "TCG doesn't
  support requested feature: CPUID.01H:ECX.x2apic"). The MSR = 0x800 + (offset >> 4) mapping is right for every
  register used: ID 0x802, VER 0x803, TPR 0x808, EOI 0x80B, SVR 0x80F, ISR 0x810-817, TMR 0x818-81F,
  IRR 0x820-827, ESR 0x828, CMCI 0x82F, timer 0x832, thermal 0x833, perf 0x834, LINT0/1 0x835/0x836, error 0x837,
  initial count 0x838, SELF_IPI 0x83F. ICR_HI (0x831, #GP in x2APIC mode) and the delivery-status poll are used
  only on the xAPIC path. EOI and ESR writes are always 0, since a nonzero x2APIC write takes #GP. CMCI is written
  only on Intel with maxlvt >= 6. The EN and EXTD transitions are legal: disabled -> xAPIC first, then xAPIC ->
  x2APIC. x2APIC is never downgraded. Writing back the BSP bit is allowed (KVM's reserved mask is 0x2FF).
  `lapicId()` returns the full 32-bit ID, and routes refuse IDs above 254.
- `irqDispatch` edge cases: vectors 0-31 never reach it (trapDispatch tests `vector >= 32` first). The fixed
  vectors 0xF0-0xF3 and 0xFE dispatch and are EOI'd (`irq_fixed_vectors_dispatch`, software `int` and a real LAPIC
  self-IPI). 0xFF and the spurious IRQ7 send no LAPIC EOI even with a vector in service (`irq_api_refused_in_handler`).
  A handler re-raising its own vector gets it once more after the EOI, with no nesting panic. Two pending vectors
  are taken highest class first, once each.
- The API from IRQ context: all 10 entry points return INVALID from inside a handler, and none takes effect: no
  vector leaks, no route is made, 0xF0 is not registered (`irq_api_refused_in_handler`).
- API misuse: double route, route after unroute, the vector or GSI already taken, unregister while routed and
  unmasked (refused) or masked (allowed), unmask without a handler, free while routed, bad flags, vectors
  0/31/32/47/0xF4/0xFD/0xFF/256/0x10030/UINT32_MAX, and GSIs UINT32_MAX, UINT32_MAX-1 and base+pins. Every case
  returns the documented status (`irq_route_misuse`, `irq_fixed_vectors_dispatch`). `irqCoreGsiLookup` cannot
  overflow (64-bit math, proven by a host mutation).
- Interrupt-context hazards: nothing a handler can reach allocates. The unhandled path goes through `klogWrite`, then
  fbcon/serial/format, and none of them calls pmm, slab, kmalloc, vmalloc or vmm (checked with grep). klog output
  runs IRQ-off, so a handler can never interrupt it. `panic()` disables IRQs first. Boot-stack headroom: across a
  full `ktest=all` run the deepest use was 4080 of 16384 bytes (scratch scan of the zeroed boot stack), leaving room
  for an IRQ frame plus `klogWrite` (about 0.6 KiB) or a nested fault report.
- `archTrapCatch` while a handler runs: `archTrapCatchSoftware` refuses while the catch is armed, and the catch
  still works afterwards (`irq_trap_catch_refused_in_handler`). A caught fault inside an `archIrqSave` section
  restores IF=1, and a catch armed at IF=0 leaves IF=0 (`trap_catch_restores_if`). The ktest runner's
  "left interrupts disabled" check fired under mutation M23 (`kernel/test/ktest.c:151`).
- paging.c UC changes against WB/WC: PAT 0x0007010600070106 makes index 3 UC. UC leaves are PWT|PCD and never set
  the PAT bit. `VMM_CACHE_MASK` is used only in paging.c. `vmm_mmio_edges` and the framebuffer case keep the WB/WC
  results unchanged.
- IOAPIC: the RTE is written low (masked), then high, then the final low, so the pin never fires half-programmed.
  Masking reads, modifies and writes only the low dword (RO bits are ignored on write). A second IOAPIC is indexed
  in parallel arrays and overlaps are rejected (host-tested), and the overlap path unmaps with the offset pointer
  `vmmMapMmio` returned.

  `/dev/kvm` world-writable, and `run-qemu.sh` then uses `-accel kvm -cpu max`, which advertises x2APIC. The PR's
  `make test` would then be the first execution of `lapic.c`'s x2APIC branch (`irq_lapic_state` asserts x2APIC mode

- `kernel/test/fbcon_test.c:74-112` writes fbcon and serial directly, outside klog's IRQ-off section. That is

- `kernelMain` ends in `archHaltForever()` (`cli; hlt`), so a normal boot takes no interrupts after "init done".
  That is fine until something needs them.

### Unverified (why)
- **x2APIC at runtime.** QEMU 8.2 TCG cannot enable it, and there is no `/dev/kvm` in this container. It was
  audited by reading (above). If CI uses KVM, the PR's CI is its first run (see the lead).
- **KVM behavior of the new ktests.** They were run under TCG only. They avoid KVM-sensitive assumptions: the
  unmasked pin is an idle PCI INTx line, and the PIT is not used.
- **What the correct behavior panics on**: a fault or `panicBug` inside a handler while a catch is armed (the
  `TryResume` `irqDepth` check), a nested IRQ, and a non-spurious 8259 vector. A ktest cannot assert on these
  without ending the run. A harness-level expected-panic test would be needed.
- **klog's IRQ-off output section.** Its race (a handler logging into a half-written line) cannot be triggered on
  demand.
- **Second IOAPIC, pins != 24, active-low or foreign-bus ISOs, NMI sources.** QEMU's MADT has none of them; only
  the pure parts are covered (host tests).

### BUG-M3.2-1: irq_spurious_vector_no_eoi cannot see an EOI on the 0xFF path
- **Severity:** S2 · **Subsystem:** int
- **Commit found at:** ed33528 (test from ff88009) · **Profile:** debug · **Config:** `run-qemu.sh --fw uefi|bios` on a `ktest=irq_spurious_vector_no_eoi,irq_api_refused_in_handler` image
- **What happened / expected:** With `lapicEoi()` added to the 0xFF return path, the test still passed. It should fail.
- **Repro:** mutation M4 (see the table above)
- **Evidence:** bios: `KTEST DONE passed=1 failed=1`, and the one failure is the new test: `irq_misuse_test.c:112: inHandler.isrAfterSpurious`
- **Root cause:** an EOI retires the highest in-service vector, and the test raised 0xFF with nothing in service, so the wrong EOI had no observable effect.
- **Fix:** 3625477 · **Regression test:** `irq_api_refused_in_handler`
