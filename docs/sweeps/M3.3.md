Suspicions checked and dropped:
- **The `timerArm`/`timerCancel`/`timeTimerIrq` state machine.** The following were each proved by a ktest. A
  sibling that has been popped but not started can be re-armed from an earlier callback in the same batch: it is
  skipped there and fires once at its new deadline. Cancelling such a sibling returns OK and its callback never runs.
  A timer armed in the past from a callback runs from a later interrupt (`irqVectorCount(0xFE)` strictly larger). A
  callback that keeps re-arming itself at deadline 0 runs once per interrupt, 50 times, with no loop inside one
  handler. A callback that cancels itself gets NOT_FOUND, and re-arm-then-cancel leaves nothing to run. Arming and
  cancelling from another IRQ handler takes effect immediately, because only the timer handler defers `reprogram`.
  256 timers due together run from one batch, in arm order. A full queue refuses the 257th timer and still lets an
  armed timer be re-armed.
- **`reprogram` root changes.** I found no path that leaves the earliest timer with the hardware unarmed:
  insert-new-root (`peek != oldRoot`), re-arm of the root (`oldRoot == t`), cancel of the root (`wasRoot`), the empty
  queue (stop), and the end of every expiry pass all reprogram. Every non-root change leaves the root's programming
  valid. `time_timer_hw_tracks_root` reads the LAPIC initial count back after each step (5000 / 2000 / 5000 /
  5000 ms / stopped / clamped).
- **Deadlines near `UINT64_MAX`.** `deadline - now` is computed only when `deadline > now`, and it is clamped to
  2^40 ns. The one-shot count then clamps to 2^32-1 (68.7 s at 62.5 MHz, read back as `far=68721ms`). In deadline
  mode, `timeScale(2^40, nsToTscMult)` is about 2^43 ticks, which cannot overflow. `UINT64_MAX`, `UINT64_MAX-1` and
  `now+2^41` stay armed and never fire, and they cancel cleanly.
- **One-shot count edges.** A delta of 0 gives count 1, never 0, which would stop the timer. 1 ms gives
  `lapicHz/1000` +0..2. Just under the clamp gives less than 2^32-1 (`time_lapic_oneshot_count_edges`).
- **`timeScale`/`timeMakeMult` ranges.** The only call sites are `timeMakeMult(hz, 1e9)` and `timeMakeMult(1e9, hz)`.
  The documented `to % from >= 2^32` refusal cannot trigger there, because one operand is 1e9 < 2^32. A 4.5 GHz TSC
  (> 2^32 Hz) works. A random host test over 200 000 rate pairs from 1 Hz to 2^40 Hz shows the floored multiplier
  loses at most `x/2^32 + 1`.
- **Calibration on counter wrap.** A 50 ms window is 178 977 ticks of a 24-bit PM timer, which wraps every 4.69 s,
  and `timeRefDelta` masks one wrap correctly. A stuck reference is rejected by `refAdvances` (2^26 TSC ticks) or by
  the 2^34-tick window bound. The HPET target `hz/20` would exceed a 32-bit counter only if the period were below
  11.6 ps (above 86 GHz), which is not a real HPET.
- **The spread ppm** can wrap only if one window measures more than 4294 times the median. It is only logged, and
  the median is unaffected.
- **HPET registers.** All accesses are 32-bit. The fields are decoded correctly: NUM_TIM_CAP is bits 12:8,
  COUNT_SIZE_CAP is bit 13, and the period is at 0x004. Tn_INT_ENB is cleared on every comparator. Writing GEN_CONF
  as `(gen & ~3) | 1` keeps the reserved bits and clears LEG_RT. Mutation M6 confirms the PIT ktest depends on that.
- **PM timer GAS.** acpi-tables.c already limits `pmTimerPresent` to space IDs 0 and 1, so the MMIO `else` branch
  never sees PCI or FFixedHW.
- **RTC decode.** Host tests cover every hour through both 12 h encodings, PM-with-0 and 0x92 in 24 h mode,
  Feb 29 in 2000 and 2100, and the century fallback. The consistency loop (up to 5 snapshots, 20 ms UIP bound) was
  checked by reading.
- **The TSC-deadline rounding.** The floored multipliers can make the deadline land a few ns before the
  monotonic `deadlineNs`. The handler then finds nothing due and reprograms with a delta of a few ns, which costs
  one extra interrupt and is never an early callback.
- **The harness watcher.** The `.walltime` file is deleted at the start of every run: a planted stale file was
  gone after a run without the wall-check ktest. A partial serial line cannot match, because the pattern needs all 9
  fraction digits and `$`. The watcher is killed and reaped after QEMU exits. `wall-check` is not the last ktest, so
  QEMU does not exit within the 50 ms poll. The make/awk escaping checks out: M3b shows the check failing with
  `3599.177 s`.

Leads (not in the scope of a fix):
- `timerInit()` on a timer that is still armed silently resets its state to IDLE while it sits in the heap, and a
  later `timerArm` then inserts it twice. The contract does not forbid this. The cheap, false-positive-free
  detection is `state == ARMED && heapIndex < count && slot[heapIndex] == t` -> `panicBug`. That is an API decision
  (a new misuse check), so it is left for the owner.
- A century register holding a bad BCD byte makes the whole RTC invalid instead of falling back to 20yy. This
  matches time-core.h ("a nibble above 9 is INVALID"), but D-180 reads as if any implausible century falls back.
