No bug was found in the decoders' code. Suspicions written down and dropped after proof:
- Huffman long-code path (`valoff[l] + code` for l >= 10) indexing below `vals`: impossible, since
  the LUT misses only when the 9-bit prefix is at or past the first unused 9-bit code, so the
  canonical code of length l is >= that length's first code (induction over l).
- Coefficient index past 63: every `jpegZigzag[k]` access is guarded by `k <= se <= 63` (sequential
  `k > 63` check, acFirst `k > se`, the acRefine do-loop's `while (k <= se)` and the `val` check).
- Strip rows/columns: `sy < 8*v` and `x*h/hmax < compW <= nbx*8`; rows past `nby` are never read
  (confirmed by the split-allocation run above).
- Restart after the reader already hit the marker: `restartSync` uses `markerPos`; a dangling FF
  at EOF gives `markerPos = size-1` and then INVALID.
- GIF frame rect `x + w`: both u16, so no u32 overflow; `gifPut` writes only inside the clipped
  rect; the disposal-3 save is packed to the clipped width and restored with the same width.
- LZW bounds: the prefix chain strictly decreases (a new entry's prefix is `prev < next`), so
  `gifExpand` terminates within the 4096-entry stack; codes are < 4096 at width 12.
- Work bound: each non-clear code draws at least one pixel, so expansion work is O(frame area).

### Save buffer in gfxGifDecode (the caller's question)
Worth a small fix, S4, not a blocker: about 10 lines. Split `gfxGifOpen` into a static
`gifOpen(..., bool wantSave, GfxGif **out)`; `gfxGifOpen` passes `true`, `gfxGifDecode` passes
`false` (then `need` counts one canvas and no save is allocated; `gfxGifNextFrame` already skips
the restore when `save == NULL`, and frame 0's disposal is never applied). The single-image block
of `gfxGifBudgetIsTheExactPeak` would then assert the smaller peak (struct + canvas) for
the disposal-3 file, and D-163's sentence on the save buffer would say "for the animation API".
Effect today: a disposal-3 GIF whose canvas is over half of `maxTotalBytes` (default 512 MiB, so a
canvas over about 16384 x 8192) cannot be opened by `gfxImageDecode`, though frame 0 alone fits.
