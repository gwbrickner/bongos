## Plan
ROADMAP.md's M2.2 steps:
1. Early bump allocator over the BootInfo map.
2. The `Page` array at the metadata region (ARCHITECTURE §6.1). Buddy allocator orders 0-10
   (4 KiB-4 MiB) with `DMA32` (<4 GiB) and `NORMAL` zones.
3. A per-CPU page cache (BSP-only for now, with the per-CPU API already in place -- real
   `CpuLocal` doesn't land until M3.5 per ARCHITECTURE §7.1, so this needs a cpu-indexed shape
   that doesn't need rewriting then, not real per-CPU state now).
4. Reclaim `LOADER_RECLAIM` memory after switching stacks -- **deferred**, see below.
5. ktests: alloc/free stress (100k ops, random orders), no-leak (free count restored), zone
   correctness, double-free detected in debug builds.

**Done when** (ROADMAP.md): the ktests pass, and `/proc/meminfo`-style totals printed at boot
match the BootInfo map.

**Step 4 deferred to M2.3, working assumption pending owner sign-off:** STATUS.md's "Questions for
owner" (recorded during M1.3) already flags that `LOADER_RECLAIM` memory holds the *live* page
tables and the loader's identity-mapped trampoline page until the kernel builds and switches to
its own CR3 in M2.3 -- reclaiming it in M2.2 would free memory the CPU is still using for address
translation. The architect subagent's proposed fix (move the reclaim to M2.3, after
`vmmSwitchToKernelPageTables` and the CR4.PGE toggle M2.3 needs anyway) is used as the working
plan for M2.2: the buddy allocator is built to accept additional zone spans later (so M2.3 can
hand it the reclaimed range with no API change), but `LOADER_RECLAIM` regions are *not* freed to
the allocator in M2.2. ROADMAP.md's M2.2 wording still needs an owner decision; not blocking since
the Done-when checks don't require the reclaim.

Consulting the `architect` subagent before implementing (memory management is on CLAUDE.md's
consult-first list) for: exact `Page` array placement/sizing math in the metadata region, the
buddy allocator's free-list/bitmap layout, the zone split logic against the BootInfo map, and the
page-cache API shape.

- **Bugs found by actually booting under QEMU** (host tests alone missed both -- recorded here per
  CLAUDE.md and worth remembering for the reviewer pass):
  1. **Boot hang.** The first `make test` run after this step hung for the full 120 s timeout.
     `pmmInit`'s HHDM coverage check was walking `pmmMap.spans` (the *widened*, order-10-aligned
     envelopes `pmmMapScan` builds so buddy merges never need a validity check) instead of the raw
     BootInfo `regions[]` list. On real QEMU output, the first USABLE region is `[0, 0xA0000)`
     (640 KiB) -- widening that to a 4 MiB span reaches into the legacy `0xA0000`-`0x100000`
     VGA/BIOS gap, which never appears in the BootInfo map *at all* (not even as RESERVED) and so
     the loader's HHDM-run builder never mapped it -- `archEarlyLookup` on that hole returned
     NOT_FOUND, which should have panicked immediately but instead the loop's leaf-size advance
     had the same bug (see next) and never made forward progress, so it turned into an infinite
     loop rather than a clean panic. Fixed by walking the exact raw `regions[]` entries (clipped to
     the HHDM window) instead of the spans -- `kernel/mm/pmm-map.c`'s `pmmTypeIsManaged` was
     exported as `pmmMapTypeIsManaged` so `pmm.c` can reuse the identical "is this a managed type"
     test the scan itself uses. While fixing this, also caught and fixed a related bug in the same
     loop: it advanced `phys` by a whole `leafSize` every iteration regardless of whether `phys`
     was actually leaf-aligned yet, which under-advances (or in a pathological case, loops forever)
     when a region's `base` isn't 1 GiB/2 MiB-aligned on its very first leaf.
  2. **`managedPages` leak.** With the hang fixed, three ktests failed with `allocatedPages` wildly
     wrong (hundreds of thousands of pages "allocated" against a 512 MiB machine). `buddy.c`'s
     `buddyFreeBlock()` incremented `zone->managedPages` on *every* call -- correct for the one-time
     population from `pmmAddFreeRange`, wrong for every ordinary `pmmFreePages()`/cache-drain
     afterward, which also routes through `buddyFreeBlock()` and so kept inflating `managedPages`
     forever as pages simply cycled through alloc/free. `tests/host/kernel_buddy_test.c`'s stress
     test never caught this because it captured `totalManaged` right after the one-time population
     and never re-checked it after the alloc/free loop. Fixed by moving the `managedPages` bump out
     of `buddyFreeBlock()` (which can't tell "first time" from "ordinary free" apart) and into
     `pmmAddFreeRange()`, the one controlled entry point that actually knows; added a regression
     assertion to the host test (`managedPages` must equal `totalManaged` after the whole 100k-op
     loop, not just right after population) and updated its `freeRangeAsBlocks()` helper to do the
     same bump `pmmAddFreeRange()` now does.

  written down before the reasoning goes stale), `docs/ARCHITECTURE.md` §23's boot-matrix row
  (mentions the optional memory column and >4 GiB test-full row, D-084).
- **Why:** the `reviewer` subagent's pass (full diff review, `git diff 6455e1a..HEAD`) found one
  Critical bug: `pmmFreePages()` called `buddyFreeBlock()` directly for order >= 1 without first
  resetting the block's head `Page` to `PAGE_STATE_TAIL` -- `buddyFreeBlock()`'s own precondition
  (every page of the block, head included, already TAIL). If the freed block happened to be the
  *upper* half of a buddy pair whose lower half was already free, the merge moves the block's
  base pfn *down* to the lower buddy's address, and `buddyFreeBlock()` only ever writes the Page
  state of that *final* merged head -- the original (upper) pfn's own Page was simply abandoned,
  still `PAGE_STATE_ALLOCATED` with its old order. A second free of that same page would then pass
  `pmmValidateForFree()`'s ALLOCATED-with-matching-order check and get treated as a legitimate
  free, silently handing out the same physical frames twice and corrupting the free lists -- the
  reviewer reproduced this independently with a small host program linking the real `buddy.c`.
  The existing `pmm_double_free` ktest's case 2 missed it entirely because whichever block that
  test happened to allocate second/free second landed on the *lower* half in practice, which
  buddyFreeBlock's final head-write does correctly overwrite -- only the upper-half direction was
  broken, and nothing forced that specific direction before this reviewer round. The other 7
  Should-fix items are all either real gaps in what the milestone's own tests could catch (thin
  poison sampling, a single-qword-per-block test tag that couldn't see an overlap, an untested
  PAT-bit assumption in a code path nothing had exercised with a PAT-set large page yet) or stale/
  garbled documentation the fast pace of implementation left behind.
