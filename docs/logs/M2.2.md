## Plan
ROADMAP.md's M2.2 steps:
1. Early bump allocator over the BootInfo map.
2. The `Page` array at the metadata region (ARCHITECTURE §6.1). Buddy allocator orders 0-10
   (4 KiB-4 MiB) with `DMA32` (<4 GiB) and `NORMAL` zones.
3. A per-CPU page cache (BSP-only for now, with the per-CPU API already in place -- real
   `CpuLocal` doesn't land until M3.5 per ARCHITECTURE §7.1, so this needs a cpu-indexed shape
   that doesn't need rewriting then, not real per-CPU state now).
4. Reclaim `LOADER_RECLAIM` memory after switching stacks -- **deferred**, see below.
5. ktests: alloc/free stress (100k ops, random orders), no-leak (free count restored), zone
   correctness, double-free detected in debug builds.

**Done when** (ROADMAP.md): the ktests pass, and `/proc/meminfo`-style totals printed at boot
match the BootInfo map.

**Step 4 deferred to M2.3, working assumption pending owner sign-off:** STATUS.md's "Questions for
owner" (recorded during M1.3) already flags that `LOADER_RECLAIM` memory holds the *live* page
tables and the loader's identity-mapped trampoline page until the kernel builds and switches to
its own CR3 in M2.3 -- reclaiming it in M2.2 would free memory the CPU is still using for address
translation. The architect subagent's proposed fix (move the reclaim to M2.3, after
`vmmSwitchToKernelPageTables` and the CR4.PGE toggle M2.3 needs anyway) is used as the working
plan for M2.2: the buddy allocator is built to accept additional zone spans later (so M2.3 can
hand it the reclaimed range with no API change), but `LOADER_RECLAIM` regions are *not* freed to
the allocator in M2.2. ROADMAP.md's M2.2 wording still needs an owner decision; not blocking since
the Done-when checks don't require the reclaim.

Consulting the `architect` subagent before implementing (memory management is on CLAUDE.md's
consult-first list) for: exact `Page` array placement/sizing math in the metadata region, the
buddy allocator's free-list/bitmap layout, the zone split logic against the BootInfo map, and the
page-cache API shape.
