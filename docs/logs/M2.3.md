## Summary
bongOS now runs on its own page tables instead of the UEFI loader's. `vmmInit()` builds a fresh
kernel PML4 from pmm-allocated pages (rebuilding a narrower HHDM from the BootInfo memory map,
mapping the kernel image with per-section permissions, adopting the Page-array subtree from the
loader's tables rather than re-mapping it, and eagerly allocating all 256 kernel-half PML4 slots
so every future address space shares them), switches CR3, reprograms the PAT (WC framebuffers),
enables SMEP/SMAP/UMIP, and verifies W^X by walking the live tables (panicking on any violation;
the boot log's `vmm: W^X verified: ...` line and two ktests with real deliberate faults prove
it's enforced, not just checked). `vmmMapKernel`/`vmmUnmapKernel` and a pure, host-tested
first-fit KVA extent allocator (`kernel/mm/kva.c`) give the kernel its first general-purpose
virtual-memory API, ready for M2.4's slab/vmalloc. `LOADER_RECLAIM` is finally freed into the
buddy allocator (`pmmReclaimLoaderMemory()`) once the loader's tables are no longer live,
recovering the last ~4 MiB the pmm couldn't touch since M2.2; `kernelBootInfo()` now returns a
pmm-backed snapshot that survives the reclaim instead of a pointer into freed memory. Designed
with the `architect` subagent (D-086/D-087/D-088/D-089/D-090); three `reviewer` rounds found one
real W^X gap (a writable KVA-region alias of kernel text was possible before the third round) and
several correctness/robustness issues in the anti-aliasing and reclaim-validation logic, all
fixed, with the final pass clean (no Critical, no Should-fix). All 28 ktests, 162 host tests, and
the full `make test`/`make test-full` harness (including the memory-diversity NORMAL-zone row)
pass with no boot errors.

  1. `archPagingVerifyWx()`'s HHDM-alias-writability check silently no-op'd for a 2 MiB/1 GiB RO
     leaf (`findLeafPte()` only understands 4 KiB) -- forced the text+rodata HHDM carve-out to

  2. The text+rodata carve-out's `roStart`/`roEnd` math could map past a KERNEL region's own

     `[base, end]`, and added an upfront panic confirming `[kernelPhysBase, roPhysEnd)` lies
     inside exactly one KERNEL region.
  3. The WC/WB anti-aliasing check used `pmmPhysToPage() != NULL` as a proxy for "the HHDM maps
     this WB", which is wrong in both directions (ACPI_NVS is HHDM-WB but pmm-unmanaged;
     FRAMEBUFFER is HHDM-WC and pmm-unmanaged, so a WB request over it was never checked) --
     replaced with a real walk of the live HHDM alias (`hhdmAliasIsWc()`).
  4. `archMapPages()` silently truncated a physical address past bit 51 and never checked
     `pa+size` overflow -- added a `physAddrLimit()` (CPUID 0x80000008 MAXPHYADDR) check.
  5. `archTlbInvalidateKernelRange()` (the one function ARCHITECTURE §6.3/M3.5 says a real IPI
     shootdown replaces) was never actually called from `archUnmapPages`/`archMapPages`'s
     rollback, which invalidated per-leaf via `archInvlpg` directly instead -- an M3.5 SMP change
     to that one function would have left `vmmUnmapKernel` doing local-only invalidation on other
     CPUs. Routed both through it.
  6. `kvaFree()`'s "cannot fail" contract (`vmm.h`) was false: a full extent table on a
     non-coalescing free returns `STATUS_ERR_INVALID`, which `vmmKvaFree()` turns into a
     `panicBug()`, reachable through ordinary (if currently nonexistent) heavy KVA use. Fixed the
     documentation to state this honestly as a recorded, accepted limit (matching D-085's own
     precedent) rather than overclaiming -- a full redesign (tracking allocated ranges too, or a
     different allocator shape) is more than M2.3's actual usage (nothing calls `vmmKvaAlloc` yet
     outside its own ktest) justifies. Added `tests/host/kernel_kva_test.c` cases for both the
     full-table case and the out-of-bounds case below.
  7. `kvaFree()` had no bounds check against its own `[base, end)` at all -- a stray out-of-bounds
     free became a free extent later handed out. Added `base`/`end` fields to `KvaState`, checked
     in `kvaFree()`, plus a matching `vmmRangeInKva()` check in `vmmKvaFree()`.
  8. `pmmReclaimPiece()` zeroed a range before validating it was entirely `PAGE_STATE_RESERVED`
     (only `pmmAddFreeRange()`'s own internal check ran afterward, by which point evidence of a
     real inconsistency would already be destroyed) -- added `pmmRangeAllReserved()`, checked
     first. Also added an HHDM-window clip (mirrors pmm-map.c's own) and a reentrancy guard
     (`pmmReclaimLoaderMemory()` now panics if called twice).
  9. `kernelBootInfo()`'s new "stays dereferenceable" contract was false for `cmdlinePhys`, which
     still pointed at the original loader page `pmmReclaimLoaderMemory()` frees and zeroes --
     zeroed it explicitly once `kernelCmdline()`'s copy exists, and narrowed the contract comment
     to say precisely which fields that promise covers (`kernel/core/main.c`,
     `kernel/include/kernel-boot.h`).
  10. `validateReservedTablePage()`'s claim to rule out a LOADER_RECLAIM page was actually
      vacuous -- LOADER_RECLAIM frames are *also* `PAGE_STATE_RESERVED` at this point in boot (the
      reclaim hasn't run yet), so the state check alone can't distinguish them from genuine bump-
      allocator memory. Added `pmmPhysInLoaderReclaim()` (`kernel/include/pmm.h`/`pmm.c`) and
      called it explicitly.
  11. `paging_fb_wc`'s comment claimed the "framebuffer ... mapped WC" line was grepped by

  12. The meminfo self-check's new `+ Reclaimed` term was tautological (derived from the exact

      added an independent sanity bound in `pmmReclaimLoaderMemory()`: reclaimed pages can never
      exceed `pmmMap.typePages[BOOT_MEM_LOADER_RECLAIM]`, computed at scan time before any of the
      reclaim logic ran.
