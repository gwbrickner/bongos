# M1.3: Kernel skeleton + real handoff

_Note: CLAUDE.md's session protocol names branches `m<p>-<n>-<slug>` (M1.2 used `m1-2-uefi-hello-loader`).
This cloud session was assigned a fixed branch, `claude/relaxed-curie-knpvwb`, by the harness, with an

## Summary
bongOS has a real kernel for the first time. The UEFI loader now reads `boot.cfg`, loads
`kernel.elf`, builds its own page tables from scratch (a direct map of all RAM plus a W^X-mapped
kernel image, using 1 GiB/2 MiB pages where the CPU supports them), gathers a random seed and the
ACPI RSDP, exits boot services with a proper retry loop, and jumps to the kernel through a small
trampoline that swaps CR3 without ever touching unmapped memory. The kernel installs its own boot
GDT and a null IDT, brings up a 16550 serial driver and `klog`, validates the BootInfo handoff ABI
byte-for-byte against ARCHITECTURE §5.3, prints a memory-map summary, and runs an in-kernel test
framework (`KTEST()`, `ktest=` on the cmdline, isa-debug-exit reporting PASS/FAIL to the harness).
`make test` now boots under OVMF and QEMU exits 33 with `KTEST PASS bootinfo_valid` in the serial
log -- the harness itself now greps for that literal line rather than trusting the exit code alone,
so the Done-when guarantee is a real, enforced gate.

Designed with the `architect` subagent first (paging and the boot handoff ABI both call for that
per CLAUDE.md), then implemented, then taken through two rounds of independent verification: a
`qemu-tester` pass confirming the build/boot claims, and two `reviewer` rounds. The first review
round found one Critical issue -- an integer-overflow bug in the ELF loader's kernel-window bounds
check that a crafted `kernel.elf` could have used to make the loader write out of bounds and map an
unintended physical page -- plus 9 Should-fix items (memory-map truncation failing silently instead
of loudly, RDSEED/RDRAND used without a CPUID check, no CR4.LA57 guard, an unwiped random seed, a
pointer dereferenced before its bounds were checked, x86 asm outside `kernel/arch/x86_64/`, and
some doc/citation cleanup). All of those were fixed and re-reviewed; the second round returned
**PASS** with 3 more Should-fix items (an actual-exploit-shape regression test that was missing,
a real out-of-bounds read in the tiny kernel `printf` on a format string that ends mid-specifier,
and a missing compiler memory barrier on `cli`/`hlt`) and several nits, all fixed in a final pass.

Two things are recorded for the owner rather than fixed here (see "Questions for owner" in
STATUS.md): a real hazard in ROADMAP.md's M2.2 step 4 (reclaiming `LOADER_RECLAIM` "after
switching stacks" is too early -- that memory holds the live page tables until M2.3), and
`BootInfo.bootDiskGuid`/`bootPartGuid` having no milestone assigned to fill them yet.

## Plan
Roadmap steps (ROADMAP.md M1.3):
1. Kernel side: `kernel.ld` (higher half at `0xFFFFFFFF80000000`, W^X section alignment), the
   entry stub (switch to kernel stack), the 16550 serial driver + `klog`, `panic()`, the ktest
   framework (`KTEST()` section registration, `ktest=` cmdline, isa-debug-exit reporting).
2. `boot/common/`: ELF64 loader, page-table builder (HHDM with 1 GiB/2 MiB pages, kernel mapping,
   trampoline identity page), BootInfo builder (`bootinfo.h` exactly as ARCHITECTURE §5.3),
   memory-map conversion.
3. UEFI loader: load `kernel.elf` + `boot.cfg` (`kernel=`/`cmdline=` only for now), call
   `ExitBootServices` with retry, jump to the kernel.
4. Kernel validates BootInfo (magic/version), prints the memory-map summary, runs its ktests.

**Done when:** `make test` shows `KTEST PASS bootinfo_valid` and exits 33 under OVMF at 1 CPU.

Touches the boot handoff ABI and the page-table builder (paging) -- both call for an `architect`
consult before implementation, per CLAUDE.md. Plan: consult `architect` for the concrete
handoff/paging/ktest design first, then implement, then `qemu-tester` to build/boot, then
`reviewer` before the PR.
