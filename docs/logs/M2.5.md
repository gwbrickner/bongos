## Plan
_Break the roadmap steps into concrete sub-steps. Note which subagents you'll consult._

Per ROADMAP.md M2.5 (`needs-owner`, needs M1.4 + M2.1, both done):
1. stage1 (440-byte NASM MBR): relocate to 0x0600, INT 13h AH=42h reads of stage2 using the
   LBA/length mkimage patches in, jump to it, print an error code and halt on failure.
2. stage2: A20 (fast A20 port, INT 15h AX=2401, 8042 fallback), E820, VBE mode pick (same rule as
   UEFI's GOP selection), RSDP scan (EBDA then 0xE0000-0xFFFFF), enter 32-bit protected mode, real
   -mode thunks back to INT 13h/INT 10h for disk/VESA calls, GPT + FAT32 readers (new shared code
   under `boot/common`, since UEFI got FAT32 for free from firmware and nothing like this exists
   yet), a boot menu (reusing `boot/common/bootmenu.c` + `boot.cfg` parsing), load kernel.elf +
   initrd above 1 MiB, build page tables + BootInfo (`bootMethod = BIOS`, shared code), enter long
   mode, jump.
3. `tools/mkimage`: install stage1 into the protective MBR's boot-code area, stage2 into the BIOS
   boot partition, patch stage2's LBA/length into stage1.
4. Harness: `tests/harness/matrix.conf`/`matrix-full.conf` gain BIOS rows; `mk/test.mk`'s `test`
   target also runs the GUI screenshot tests under `--fw bios`; new `tests/gui/ref/bios-*.png`
   references.

Design consulted with the `architect` subagent first (this is a boot-handoff-adjacent milestone
per CLAUDE.md's subagent rule) before writing any stage1/stage2 code. Result: D-099 through
D-112 in DECISIONS.md, plus `docs/specs/bios-boot.md` (byte-level layouts) and ARCHITECTURE.md
updates (§2 `boot/common/hw/`, §5.1 pointer to the spec, §5.4 BIOS addendum, §5.5's video-mode
rule refined to require <=8-bit color channels, §5.6 rewritten to the real step order --
D-103 supersedes the literal E820/VBE/RSDP-before-PM order in the original wording, since VBE
needs `boot.cfg`'s `resolution` which needs GPT+FAT32+the parser first).

Implementation order (architect's plan, one commit per step, each independently buildable/
testable against real QEMU via the `qemu-tester` subagent, UEFI kept green throughout):
1. `boot/common/hw/` split (serial, libc-shim, +new cpu.c) -- refactor only, UEFI unaffected.
2. Shared menu-ui extraction from `boot/uefi/menu.c`.
3. `bootvideo.c` (shared mode-selection rule) + refactor `gop.c` onto it.
4. `boothandoff.c` (shared page-table/BootInfo builder) + thin down `boot/uefi/handoff.c`.
5. Pure, host-tested BIOS-only modules with no hardware coupling yet: `memMapE820TypeToBootMem`,
   `bootheap`, `bootacpi`, `bootkey`, `bootcrc32`, `bootgpt`, `bootfat`, the `elf.c` size_t fix,
   `tools/mkimage/biosboot.c`.
6. `mk/bios.mk` + stage1.asm + a stage2 skeleton (16-bit entry only, prints over COM1) +
   mkimage `--stage1`/`--stage2` install. First real QEMU boot test of anything BIOS-side.
7. A20, PM switch, fault IDT, `rmInt`/`rmIdle`, `stage2Main` skeleton with serial + CPU check.
8. E820 + heap wired into stage2.
9. Disk: EDD -> GPT -> FAT32 -> read `boot.cfg`.
10. VBE mode pick + set.
11. Kernel load, RSDP, random seed, shared handoff, long mode jump -- first full BIOS boot to
    the kernel. Add `bios 1` to `tests/harness/matrix.conf`.
12. BIOS menu input loop; GUI screenshot tests under `--fw bios`; `matrix-full.conf` BIOS rows.
13. Docs polish, `reviewer` subagent pass(es), PR.

### 2026-09-28 10:00: step 7 (part 3, final), the real-mode thunk -- and a real bug found+fixed
- **Changed:** `boot/bios/stage2/rm.h` (the `RmRegs` struct + `rmInt`/`rmIdle` declarations,
  D-102) and `boot/bios/stage2/rm.asm` (the implementation: drops to real mode, loads every
  `RmRegs` field into its matching register/segment, executes `pushf` + a far call through the
  live IVT entry -- not a self-modifying `int imm8`, not v86 mode -- captures every result
  register/segment/FLAGS, and returns to protected mode). `boot/bios/stage2/main.c`'s
  `thunkSelfTest()` now calls `rmInt(0x12, &r)` (INT 12h, get conventional-memory size) as the
  first real exercise of the thunk. **Deliberately deferred** (not part of this step): the PM-only
  fault IDT D-102 groups with the thunk -- a debugging aid for catching a stray fault with a
  diagnostic instead of a silent triple-fault, not required for correctness; QEMU's own
  `--debug` (`-d int,cpu_reset`) logging covers that need during this milestone's own development,
  so building an in-guest version is left for later if it turns out to be worth the added
  complexity.
- **Why:** ROADMAP M2.5/D-102 -- every remaining BIOS-side step (E820, disk reads, VBE) needs a
  way to call real BIOS interrupts from stage2's C code once it's past the one-way A20/PM switch.
- **A real bug, found and fixed via booting under real QEMU (not just reasoning about the asm):**
  the first working version hung completely after the BIOS call returned successfully (confirmed
  via 9 temporary serial checkpoints threaded through every stage of the transition -- all 9
  fired, meaning the PM->RM->PM round trip and the BIOS call itself were correct). Root cause,
  found with GDB attached to QEMU's gdbstub: `rmInt`'s real-mode window deliberately loads the
  caller's requested `RmRegs.ebp` into the *live* EBP register (some BIOS calls take/return
  values there), but EBP doubles as `rmInt`'s own C-style frame pointer -- so by the time
  execution returns to protected mode, EBP no longer holds the saved frame pointer. The original
  epilogue's `mov esp, ebp` (restoring the stack the "normal" way) used this clobbered value,
  landing ESP near address 0 and popping a garbage "return address" (0xF000FF53, deep in the
  BIOS ROM reset-vector area) into EIP -- confirmed directly by breaking at the `ret` instruction
  and inspecting `$esp`/the stack contents. Fix: removed `mov esp, ebp` entirely. It was already
  redundant (the four prologue pushes are popped in exact reverse order first, which
  arithmetically lands ESP at the same place `mov esp, ebp` would have -- this was verified by
  hand before the bug was found, which is exactly why deleting the line was safe) and, now that
  EBP can't be trusted after the real-mode window, actively wrong. `rmIdle`'s epilogue keeps its
  own `mov esp, ebp`, since its real-mode window never touches EBP.
- **Tests:** bisected with 9 temporary single-character serial checkpoints threaded through every
  stage of `rmInt` (confirmed the bug was in the *epilogue*, after the BIOS call had already

### 2026-09-28 (step 8, continued): a second real thunk bug -- ES/DS loads clobbering EAX
- **Root cause, found by direct QEMU debugging** (temporary serial probes, not guessing): a raw
  manual INT 15h/E820h call showed CF=1, EAX=0x00008600 -- SeaBIOS's generic "function not
  supported" response (`RET_EUNSUPPORTED`). Testing INT 15h AH=0x88 (a much older, universally-
  supported subfunction with none of E820h's complexity) got the *same* generic failure, ruling
  out anything E820-specific. Dumping the live IVT[0x15] entry confirmed it resolved to a real,
  sane BIOS ROM address (`0xF000:F859`, right next to IVT[0x12]'s `0xF000:F841`) -- the call
  really was reaching genuine BIOS code, which was genuinely deciding "not supported". A probe
  that wrote EAX to a fixed scratch address *immediately before* the actual `call far` found the
  answer: EAX was 0x00000000 going in, not 0xE820 or 0x8800 as requested. `rm.asm`'s real-mode
  window loaded the caller's requested EAX/EBX/.../EBP first, then loaded ES and DS *last* via
  `mov ax, [...]; mov es/ds, ax` -- but `ax` is EAX's low 16 bits, and for any call whose input
  ES/DS were 0 (essentially every real caller, including both failing tests here), that reload
  overwrote exactly the bits the BIOS was about to dispatch on. INT 12h's self-test never caught
  this since it passes no input registers at all -- the same shape of bug as step 7's `ebp`
  clobber (a segment/lookup mechanic reusing part of a register the caller's real value was
  already sitting in), this time in the *load* side rather than the epilogue.

  scratch, before EAX holds anything the caller asked for), then EAX/EBX/ECX/EDX/ESI/EDI/EBP load
  last, immediately before `sti`/`pushf`/the call. Every one of these reads now goes through
  `fs:` (not plain `ds`-relative addressing, which the old order depended on to stay valid) so
  the new order never depends on what `ds` currently holds.
