## Summary
bongOS has a graphical boot: the UEFI loader picks a GOP video mode (auto-selecting the largest
mode up to 4K, or an exact `resolution=` match), draws an interactive boot menu with arrow-key,
Enter, and digit-key selection (on screen and mirrored to serial), and hands the kernel a real,
HHDM-mapped framebuffer. `boot.cfg` grew a full grammar: `[Name]` sections with `kernel`/`initrd`/
`cmdline`/`resolution`/`kaslr` inheriting from a global scope, plus `timeout`/`default`, validated
both at image-build time (`tools/mkimage`) and by the loader itself, with a line-numbered error on
anything malformed. The kernel's new `fbcon` driver -- a scrolling text console built on a shared
glyph-blit primitive the loader's menu also uses -- mirrors every `klog` line onto the screen in
color, drawing an original 8x16 bitmap console font authored from scratch for this project (no
third-party font). The whole pipeline is now screenshot-tested end to end: `tools/imgdiff`, a
from-scratch PPM/PNG/DEFLATE codec, diffs QEMU screendumps against checked-in references, driven
by a new QMP-scripting test harness that types boot-menu key presses over the emulated serial port
and waits for exact log lines and framebuffer content to match.

Designed with the `architect` subagent first (the boot handoff ABI, the GOP framebuffer's HHDM
mapping, and the boot.cfg grammar all call for that per CLAUDE.md), then implemented in 7 steps,
each committed and verified independently: the boot.cfg parser, the console font, shared
loader/kernel drawing code, GOP + the interactive menu, the kernel's fbcon + ktests, the imgdiff
codec, and finally the GUI test harness itself. Actually running the finished harness against live
QEMU -- not just building it -- caught two real bugs before they could ship: a stray pixel in the
font's 'O' glyph (a Python aliasing mistake in the one-off font-generation script) and a loader
ordering bug where `EFI_SIMPLE_TEXT_INPUT_PROTOCOL.Reset()` ran after the menu's "ready" sync
marker instead of before, silently swallowing a keypress that arrived quickly after it. Both fixed
and reverified; full details in the Log below.

Records decisions D-067 through D-070 in `docs/DECISIONS.md` (the boot.cfg grammar, GOP mode
selection + the framebuffer's HHDM mapping exception to D-059, the original console font, and the
screenshot-test approach), and updates `docs/ARCHITECTURE.md` §5.2 through §5.5 to match (the full
boot.cfg grammar, `pitch` being bytes, the framebuffer HHDM mapping, and the GOP-before-menu boot
order).

## Plan
Roadmap steps (ROADMAP.md M1.4):
1. Loader: GOP mode selection (ARCHITECTURE §5.5 step 5, plus a `resolution=` override), fill
   `BootInfo.fb`.
2. Kernel `fbcon`: an 8x16 bitmap font (`data/fonts/console.psf`), scrolling and colors, mirrors
   klog.
3. Full `boot.cfg` parser with `[entry]` sections, `timeout`, and `default`. Menu on screen and
   serial (arrow keys + Enter; on serial, number keys).
4. Harness: QEMU `screendump` at the boot menu and after the kernel banner, compared with
   `tools/imgdiff` (introduced here) against reference PNGs.

Design questions to run past the `architect` subagent before implementing (on-disk format +
boot-handoff-adjacent, per CLAUDE.md): the exact `[entry]`-section boot.cfg schema (ARCHITECTURE
§5.2 lists the keys and the three default entries but not per-entry vs. global scoping, or the
`default`/`timeout` key semantics precisely), how the PSF font is embedded and consumed, and the
screenshot-test comparison approach (`tools/imgdiff` threshold/format).
