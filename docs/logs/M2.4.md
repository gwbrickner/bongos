## Plan
ROADMAP M2.4 steps: (1) slab caches with constructors and per-CPU magazines; `kmalloc` size
classes 16-8192 bytes; (2) `vmalloc` for large, page-granular allocations with guard pages, built
on M2.3's `vmmMapKernel`/`vmmUnmapKernel` and KVA allocator (`kernel/mm/vmm.c`/`kva.c`); (3)
debug-build poisoning, redzones, and double-free/use-after-free detection; (4) ktests for stress,
alignment, redzone overflow, and a guard-page fault. Needs: M2.3 (done).

Sub-steps:
1. Consult the `architect` subagent for the design: slab cache/magazine layout, size-class table,
   `Page.privateWord` usage (reserved for this per page.h), the debug poison/redzone/double-free
   scheme and its relationship to D-082's `archTrapCatch`/`TRAP_CATCH_KERNEL_BUG`, and the
   kmalloc/vmalloc header API shape. Record as D-092+.
2. Implement the slab allocator core (cache create/alloc/free, per-CPU magazines -- BSP-only for
   now per M2.2's precedent, real per-CPU arrives M3.5).
3. Implement `kmalloc`/`kfree` on top of it (fixed size classes 16..8192).
4. Implement `vmalloc`/`vfree` on top of `vmmKvaAlloc`/`vmmMapKernel` (guard pages already built
   into `vmmKvaAlloc`).
5. Debug-build (`KERNEL_DEBUG`) poisoning/redzones/double-free/UAF detection, wired through
   `panicBug()`/`archTrapCatch` the way pmm's D-082 does.
6. ktests: stress, alignment guarantees, redzone-overflow detection, guard-page fault. Host tests
   for any pure logic (size-class math, free-list bookkeeping) that doesn't need real paging/pmm.
7. `qemu-tester`: `make test`/`make test-full`, `make host-tests`, `make format-check`.
8. `reviewer` pass(es); fix Critical/Should-fix.
9. Update ROADMAP.md/STATUS.md, write Summary, open PR (`needs-owner: yes`).

### 2026-09-26 (4): slab/kmalloc/vmalloc implemented; one real bug found and fixed via QEMU
- **Changed:** implemented the whole subsystem per D-092..D-097: `kernel/include/kmalloc.h`/
  `vmalloc.h` (public API), `kernel/mm/slab-internal.h` + `slab-core.c`/`slab-debug.c` (pure
  layout/bufctl/redzone/poison math, host-tested), `kernel/mm/slab.c` (cache create/destroy/
  alloc/free, one coarse-locked magazine per cache -- D-094's simplification of the architect's
  three-tier lock proposal -- and kmalloc/kfree's 12 size classes), `kernel/mm/vmalloc.c`. Wired
  `slabInit()`/`vmallocInit()` into `kernelMain` right after `pmmReclaimLoaderMemory()`. Added
  ktests: `kmalloc_stress`, `kmalloc_alignment`, `kmalloc_double_free`, `slab_ctor_dtor`,
  `kmalloc_redzone_overflow`/`kmalloc_poison_detects_uaf` (KERNEL_DEBUG), `vmalloc_guard_page_faults`,
  `vmalloc_map_free_no_leak`, `vmalloc_interior_free_rejected`. Host test
  `tests/host/kernel_slab_test.c` for the pure core.
- **A real bug, caught only by booting under real QEMU (not host tests):** `kmalloc_stress`
  faulted with a wild pointer hundreds of MB past the machine's actual RAM. Root cause:
  `slabComputeLayout()` computed `objOffset` (where slot 0's *payload* starts) as just past the
  header+bufctl array, but didn't reserve room for slot 0's own *left redzone*, which sits
  `[objOffset-rzLeft, objOffset)` -- for several size classes (first caught on kmalloc-1024) that
  region reached backward into the bufctl array itself, so a fresh slab's KERNEL_DEBUG carve-fill
  overwrote the free list's own link values with `0xBBBB` redzone bytes. `slabFreeListPop()` then
  faithfully returned that garbage as a "valid" object index, computing an address far outside
  the slab. Bisected via targeted, temporary klog instrumentation (not left in the tree) that
  narrowed it from "wild pointer somewhere in slabAlloc" down to "the very first free-list pop
  after a fresh carve returns idx=0xBBBB" in a couple of rebuild/boot cycles. Fixed in
  `slab-core.c` (`slabMinObjOffset()` now folds `rzLeft` into `objOffset`'s lower bound), and
  strengthened the *existing* host-test invariant (`slabComputeLayoutInvariantsAllClasses`) to
  assert `objOffset - rzLeft >= header+bufctl` directly -- it was checking `objOffset` alone
  before, which is exactly the gap that let this ship past host tests in the first place. Also
  found and fixed two bugs in the *tests themselves*, both self-inflicted: `slab_ctor_dtor`
  explicitly clobbered its object before freeing it, then asserted the ctor's signature survived
  the free/realloc -- of course it didn't, since a ctor cache's contract is "never reset between
  allocations except at carve time," not "always show the ctor's value"; removed the clobber.
  `kmalloc_stress`'s size==1 case wrote the "end tag" to `bytes[size-1]`, which for size 1 *is*
  `bytes[0]`, so it silently overwrote its own start tag; guarded both the write and the check on
  `size > 1`.
- **Why:** CLAUDE.md's session protocol (implement incrementally, verify against real QEMU, not
  just host tests) -- this is exactly the kind of bug host tests alone can't catch (it only
  manifests once a `KERNEL_DEBUG` carve actually runs against a real slab page), which is why
  ARCHITECTURE's own testing philosophy insists on booting the real thing, not just `host-tests`.
- **Tests:** `make host-tests`: 171/171 (163 before this milestone + 8 new: 2 kva liveCount
  tests replacing the one D-098 obsoleted, 6 slab-core/slab-debug tests). `make test`: 37/37
  ktests pass (28 before + 9 new), no boot errors, both before and after `make format`.
  `make format-check` clean.

### 2026-09-27: reviewer round -- no Critical, 7 Should-fix items, all fixed
- **Changed:** the `reviewer` subagent found no Critical findings on the full milestone diff but
  7 Should-fix items, all fixed:
  1. A latent hazard: `slabGrowLocked()`/`slabReleaseToPmmLocked()` called `pmmAllocPages()`/
     `pmmFreePages()` (which can themselves call `pmmBug()`) and ran caller-supplied ctor/dtor
     callbacks while `slabLock` was held -- a caught `panicBug()` longjmp in that state would
     leave IRQs disabled forever, exactly the hazard `pmmBug()`'s own contract comment warns
     about. Restructured into `slabGrow()`/`slabReleaseToPmm()` (never called with the lock held)
     plus `slabRefillLocked()`/`slabReclaimEmptyLocked()` now taking `uint64_t *irqFlags` so they
     can drop and reacquire the lock around each such call, updating the caller's own saved flags
     in place. Also swapped carve-fill and ctor order (debug redzone fill now runs first, so a
     ctor that overflows its own object gets caught the normal way, via `slabAlloc()`'s redzone
     check on first use, instead of being silently overwritten by the fill).
  2. `vmalloc_map_free_no_leak` only checked vmalloc's own counters, which change on every call
     whether or not a frame was actually freed -- added a real pmm-stats before/after snapshot
     (with a warm-up round trip first, so M2.3's never-freed page-table pages don't skew it).
  3. `kmalloc_double_free` only covered the double-free-while-magazine-cached path -- added a
     case that flushes the object onto its slab's own bufctl free list first (`slabCacheShrink()`)
     before the second free, exercising the other half of the check.
  4. D-095's new `PMM_BUG_OWNED_PAGE` pmm check had no test at all -- added
     `pmm_owned_page_rejected` (kernel/test/pmm_test.c). Also added `SLAB_BUG_VMALLOC_POINTER`
     (kfree of a live vmalloc pointer) and `VMALLOC_BUG_NOT_VMALLOC` (vfree of a KVA mapping built
     directly on vmmKvaAlloc/vmmMapKernel, bypassing vmalloc entirely) sub-cases.
  5. `vmalloc`'s partial-failure unwind path had no test, and `vfree()`/`vmallocUnwind()` ignored
     `vmmUnmapKernel()`'s Status before freeing the frame anyway -- added `vmalloc_oom_rollback`
     (deliberately exhausts the pmm to exactly 3 free pages, then asks for 8) and a Status check
     (`vmallocBug(VMALLOC_BUG_CORRUPT)` on failure) in both places, plus a defense-in-depth check
     in `vfree()` that the guard page right past the mapping is genuinely unmapped (catches a
     corrupted `area->pages` that's too small).
  6. `slabCacheDestroy()` trusted its argument completely -- `cache - slabCaches` was UB for an
     out-of-bounds pointer, and a double destroy or use-after-destroy went undetected. Added
     `SLAB_CACHE_MAGIC` (set at create, cleared at destroy) and `slabCacheIsLiveLocked()` (bounds +
     in-use + magic), checked by `slabCacheDestroy()`, `slabAlloc()`, and `slabCacheGetStats()`.
  7. STATUS.md was stale (still said "just started" after implementation was actually done) --
     updated.
  Nits also fixed: `slab_ctor_dtor` now asserts `kmallocDtorCount == 0` after the free/realloc and
  the refused destroy (the earlier fix removed the object-clobber, but nothing was checking the
  destructor side of the same claim); a magazine-flush round is nulled out immediately after being
  pushed back to its slab (defense in depth against a caught mid-flush panic handing the same
  object out twice -- only reachable via corruption); a comment documenting the double-free
  check's two-critical-section window as an M3.4/M3.5 concern, not today's; `vmallocUnwind()` now
  clears `area->magic` before freeing it, matching `vfree()`; doc-comment fixes across
  kmalloc.h/vmalloc.h (a contradictory "IRQ-safe"/"must not be called from IRQ context" pair, an
  overclaimed "a double free panics" that's only true until the KVA range is reused, a wrong
  "(or its first slab)", and several missing lock/IRQ/sleep contracts); D-093 corrected to name
  `rzLeft` in the `objOffset` formula (it was written before the redzone-overlap bug fix); added
  `kvaFreeStillRejectsExplicitlyFullTable` (tests/host/kernel_kva_test.c) to directly exercise the
  defense-in-depth branch D-098's admission cap makes unreachable through kvaAlloc()/kvaFree()
  alone, by poking `KvaState` fields directly.
- **A second bug, again only caught by booting under real QEMU:** the new
  `pmm_owned_page_rejected` ktest itself had a test-accounting bug -- its vmalloc sub-case could be
  the very first `vmalloc()` call in the whole ktest run (alphabetical file order puts pmm_test.c
  before vmalloc_test.c), which would grow the vmalloc-area cache's first backing slab mid-test;
  that slab isn't reclaimed just because the one object allocated from it gets freed back
  (`slabReclaimEmptyLocked()` only runs on a magazine-full flush or an explicit shrink), so it
  looked like a genuine 1-page leak. First fix attempt (warm up vmalloc alone) wasn't enough --
  kmalloc-16 had the same problem from its own side, depending on what state earlier
  `kmalloc_test.c` tests happened to leave its cache in. Fixed properly: `slabShrinkAll()` for a
  clean baseline, then warm up *both* kmalloc-16 and vmalloc (deliberately with no shrink after
  either), then take the before/after snapshots around that stable baseline.
- **Why:** CLAUDE.md: fix every Critical (none found) then every Should-fix, or explain why not.
- **Tests:** `make host-tests`: 172/172. `make` (both plain and KERNEL_DEBUG) compiles clean.
  `make test` is being re-run now to confirm the second (test-accounting) bug's fix; see the next
  log entry for the result.
