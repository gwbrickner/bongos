# M2.1: GDT, IDT, exceptions, hardening runtime
**Branch:** `claude/amazing-goldberg-vw0vtv` · **Started:** 2026-09-25 · **State:** in progress

## Summary
bongOS now catches its own CPU exceptions instead of triple-faulting. `kernelMain` installs a
real GDT/TSS/IDT (D-072): all 32 exception vectors are 64-bit interrupt gates, with IST1/2/3
(each a dedicated 16 KiB stack behind its own unmapped guard page) reserved for #DF/NMI/#MC so a
stack-related fault can't recursively corrupt its own handler's frame. A shared `isr.asm` stub
dispatches every vector to `archTrapDispatch()`, which prints the vector/error code/registers/
control registers (with #PF/selector-error decoding) and a **symbolized** backtrace before
failing the ktest or halting; `#BP` (`int3`) is never fatal. The kernel embeds its own symbol
table (`ksyms`, D-073) via a two-pass link verified by `tools/mksyms --check`, so `symbolize()`
and `backtracePrint()` need no debug info at runtime. `__stack_chk_guard` is now derived from the
real boot entropy (`BootInfo.randomSeed`) instead of a fixed constant (D-074), and a UBSan
runtime with bongOS's own handlers is compiled into debug builds (D-075). A new ktest recovery
mechanism (`ktestArmExpectedPanic` + `archJmpSave`/`archJmpRestore`, D-076) lets a ktest
deliberately provoke a real #UD, #PF, #DF, stack smash, or UBSan violation and assert on the
result without ending the whole ktest run. Nine new ktests exercise all of this end to end,
including a real double fault delivered on IST1 and a stack-smash panic whose backtrace is
checked byte-for-byte by the test harness.

### 2026-09-25: architect design received; implementation done and green
- **Changed:** the full M2.1 implementation, following the `architect` subagent's design almost
  exactly (one deliberate deviation, below):
  - `kernel/arch/x86_64/kernel.ld`: 7 PT_LOADs (adds IST1/2/3 stacks, each with its own unmapped
    guard page below it, plus a `.ksyms` output section in `:rodata`); `kernel/include/
    sections.h` gained the matching linker symbols.
  - `kernel/arch/x86_64/cpu-tables.c` (+ `cpu-load.asm` for `lgdt`/`ltr`/`lidt`, plus the three
    IST stack reservations): builds and installs the real GDT (D-072's exact selector layout,
    including the deliberately-null 0x18 "user code32" placeholder), the 104-byte TSS
    (`iopbOffset=104`, `rsp0=0` until M4), and the IDT (all 32 exception vectors as interrupt
    gates at DPL0, IST1/2/3 wired to #DF/NMI/#MC).
  - `kernel/arch/x86_64/isr.asm`: one 16-byte-stride stub per vector (`times 16-($-...) int3`
    pads/enforces the stride), a shared `isrCommon` that saves all 15 GPRs, builds a "fake" frame
    record so an ordinary rbp-chain backtrace taken from inside `archTrapDispatch` continues
    naturally into the interrupted code, then calls `archTrapDispatch(TrapFrame*)`.
  - `kernel/arch/x86_64/trap.c` (+ `kernel/arch/x86_64/include/trap-frame.h`, arch-private):
    exception-name table, `#PF`/selector error-code decoding, the register/control-register
    dump, `#BP` handling (never fatal, just logs and resumes), and the expected-trap mechanism
    (`archTrapExpect`/`archTrapExpectTake`) ktests use to safely provoke a real #UD/#PF.
  - `kernel/core/panic.c`/`panic.h`: `panicTrap()` alongside `panic()` (shared `panicV`), a
    `panicDepth` recursion guard, and -- **the one deliberate change from the design sketch** --
    the full banner/frame-dump/backtrace print now happens *before* checking for a matching
    ktest expected-panic recovery, not after, so a caught panic still leaves the same symbolized
    report in the log a real one would (needed to satisfy the Done-when guarantee once the
    recovery mechanism means most ktest panics never reach the old fatal exit path at all --
    see the `_check-ktest-pass` bug below).
  - `kernel/core/backtrace.c`/`kernel/include/backtrace.h`: `backtraceCapture`/`backtracePrint`,
    walking known stack ranges (boot stack + the three IST stacks), symbolizing return addresses
    at `pc-1` per D-073 but printing the real `pc`'s offset.
  - ksyms (D-073): `kernel/include/ksyms-format.h` + `kernel/core/ksyms-decode.c` (pure,
    dependency-light decoder, shared by the kernel, `tools/mksyms --check`, and the new host

    `kernel/arch/x86_64/ksyms.asm` (`incbin`, blob path via a `-D` nasm define),
    `tools/mksyms/main.c` (a from-scratch ELF64 symtab reader + front-coding encoder -- kept as

    tightly coupled), `docs/specs/ksyms.md`. `mk/kernel.mk` now links the kernel twice (an empty
    placeholder blob, then the real one from `tools/mksyms`), with `tools/mksyms --check`
    verifying byte-equality against the final embed as part of the build.
  - `kernel/core/stack-protector.c`/`kernel/include/stack-protector.h`: `stackGuardInit()` folds

  CLAUDE.md's rule for interrupts/exceptions).
- **Tests:** found and fixed a real bug the hard way. First `make test` run: 3 of the 9 new
  ktests failed (`trap_df_on_ist1`, `stack_smash_detected`, `ubsan_overflow_detected`), each
  landing in its own "unreachable" branch despite `panic.c` printing "ktest: expected panic
  caught" first. Root cause (confirmed by disassembling the linked kernel): the original design
  wrapped `archJmpSave` in a `ktestExpectPanic(ktestCtx, prefix)` C function, `returns_twice`.
  That wrapper's own epilogue (`pop rbp; ret`) depends on reading its *own* return-address stack
  slot at resume time -- but a sibling call made between the two "returns" (`archKtestDoubleFault
  ()`, `ktestSmashOuter()`, or the compiler-generated call to the UBSan handler) reuses that exact
  stack slot for its own return address first, so by the time the panic recovers and jumps back,
  `ret` reads the *wrong* address (right after the sibling call, not right after
  `ktestExpectPanic`) and skips straight into the "unreachable" branch. Fixed by dropping the
  wrapper entirely: `archJmpSave` is now called *directly* from each KTEST() body (the same
  restriction real `setjmp` has, and for the same reason), with prefix-arming split into an
  ordinary `ktestArmExpectedPanic()` helper called just before it. Also found, while getting
  `make test` green: `_check-ktest-pass`'s new symbolized-backtrace grep initially failed even
  with all ktests passing, because a *recovered* panic never reached the old print-then-exit
  code path at all -- fixed by moving the banner/frame-dump/backtrace print in `panicV()` to
  before the expected-panic check, not after (see above). Final state, all green: `make
  format-check`, `make host-tests` (140/140, including 9 new `ksyms_test.c` cases), `make image`
  (debug and `RELEASE=1`, from a clean `build/`), `make test` (ktest matrix + GUI screenshot
  tests + countdown smoke), `make test-full`.
