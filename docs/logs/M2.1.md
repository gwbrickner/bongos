## Plan
Roadmap steps (ROADMAP.md M2.1, needs M1.3 which is merged):
1. Kernel GDT (§7.1 layout) + TSS with IST1-3. IDT with all 32 exception stubs. The handler
   prints the vector, error code, registers, CR2, and a symbolized backtrace.
2. Embed a compressed kernel symbol table in the image (post-link step) and add `symbolize()`.
3. Stack protector runtime (`__stack_chk_guard` seeded from `BootInfo.randomSeed`), plus the
   UBSan runtime with our own handlers (debug builds).
4. ktests: `int3` resumes; a deliberate #PF is reported with the correct CR2; a deliberate #UD is
   caught; a stack smash is detected.

**Done when:** those ktests pass, and panic output includes a symbolized backtrace.

Consulted the `architect` subagent first (interrupts/exceptions/the boot handoff are all on
CLAUDE.md's consult-first list) for: the exact GDT/TSS/IDT layout and IST stack allocation (no
real memory allocator exists until M2.2/M2.4, so this is BSP-only and statically allocated for
now -- SMP bring-up is M3.5, much later); a macro-generated exception-stub table instead of 32
hand-written near-duplicates; the C-level TrapFrame/handler design; how "compressed kernel symbol
table" should work without any third-party code (post-link extraction + a from-scratch encoding,
matching the `tools/mkfont`/`tools/imgdiff` precedent of from-scratch host tooling); which
`__ubsan_handle_*` entry points are actually needed; and -- the trickiest part -- how a ktest can
deliberately trigger #PF/#UD/a stack smash and have the handler recognize "this was an expected
test fault" and report ktest PASS/FAIL then continue running the *next* ktest, rather than
panicking the whole kernel (matching "int3 resumes").

### 2026-09-25: `backtrace_symbolized` ktest was genuinely broken -- found and fixed by hand
- **What happened:** the delegated `qemu-tester` run hit its own turn limit twice without
  reporting (a real anomaly worth noting, not brushed past); rather than keep waiting on it, ran
  the exact same check directly and boundedly myself (`tests/harness/run-qemu.sh` with an explicit
  `timeout`) and got a real, reproducible result immediately: `KTEST FAIL backtrace_symbolized:
  kernel/test/ksym_test.c:60: cmdlineGlobMatch("chainB+*", buf)`. `ksym_lookup` passed cleanly --
  the symbol table and lookup logic (KSYM v1 itself) were never the problem.
- **Root-caused with real evidence, not guesswork:** added temporary debug logging (raw stack
  words, captured addresses, function addresses) and `objdump`'d the actual linked `kernel.elf` at
  each step rather than trusting assumptions about what the compiler emitted. Two distinct, real
  bugs, found in this order:
  1. **Stack-reuse bug (the original design flaw):** the test captured `chainC`'s frame pointer
     into a global, then called `backtraceCapture()` from the *caller* after `chainA()` had
     already returned. The memory chainC's frame occupied is immediately free for reuse once it
     returns; the debug dump caught this directly -- the saved-rbp/return-address slot at the
     captured frame pointer had already been overwritten (by the very next call in the test
     function itself) by the time it was read, showing the raw stack-protector canary constant
     and other garbage instead of real addresses. Fixed by moving the `backtraceCapture()` call
     *inside* `chainC()`, so the walk happens while the whole A->B->C chain is still live on the
     stack -- only the resulting plain `uint64_t` addresses need to survive past the return, not
     the stack memory itself.
  2. **Tail-call optimization (introduced by my own fix for #1):** the rewrite for #1 also
     (accidentally) dropped an `asm volatile("")` barrier the original draft had after `chainB()`/
     `chainC()`'s calls. Without it, `chainA`/`chainB` -- whose entire body is a single call to the
     next function -- are sibling-call candidates at `-O1`: confirmed via `objdump` that they'd
     compiled to `push rbp; mov rsp,rbp; pop rbp; jmp chainB/chainC` instead of a real `call`,
     collapsing the intended 3-deep chain into effectively one frame. Fixed by restoring the empty
     `asm volatile("")` after each call, which gives the compiler something it must still do
     afterward so the call can no longer be in tail position -- verified via `objdump` that both
     functions now compile to a real `call`/`pop rbp`/`ret` sequence.
  - Also worth recording: a subagent I'd delegated the live-boot check to independently arrived at
    the tail-call diagnosis on its own (after taking a very long time and needing multiple nudges
    to finish) -- useful independent corroboration once it landed, but it arrived well after I'd
    already root-caused and fixed both issues by hand via direct `objdump`/debug-log evidence
    rather than waiting on it.

- **Changed:** `kernel/arch/x86_64/test/trap_test.c` (`trap_pf_read_cr2`, `trap_pf_write_error_code`,

- **Why:** ROADMAP M2.1's last Done-when item -- these are what actually exercise the mechanism
  built in part 1, not just prove it compiles and doesn't regress anything.
- **Two real bugs found and fixed by actually running these against QEMU, not just compiling them:**
  1. `stack_protector_detects_smash` first used `memset(buf, 0x41, 64)` on an 8-byte `char buf[8]`
     -- reasoning it needed to "definitely" overflow into the canary. `objdump` on the compiled
     frame (`push rbp; mov rbp,rsp; sub rsp,0x10`, buf at `rbp-0x10`, canary at `rbp-0x8`) showed
     this 64-byte write reached far past the canary: through `stackSmashTrigger`'s own saved RBP
     and return address, *and* into `archTrapCatchCall`'s frame (trap-entry.asm), clobbering the
     exact stack slot `TrapCatchCtx.rsp` points at -- the one real dependency `archTrapCatchResume`
     has on stack contents (its final `ret` pops the return address *from* that slot; every other
     saved register comes from the global `trapCatch.ctx` snapshot, safe from stack corruption).
     Overwriting it with repeating `0x41` bytes produced a non-canonical jump target on resume,
     turning the intended catch into a real, uncaught `#GP` (confirmed live: `KTEST FAIL
     stack_protector_detects_smash: panic: exception #GP General Protection (vector 13)`) instead
     of the clean `TRAP_CATCH_STACK_SMASH` catch the test meant to prove. Fixed by bounding the
     overflow to 24 bytes -- covers `buf`, the canary, and `stackSmashTrigger`'s own saved RBP
     (never read again once the mismatch is detected, since that path calls `__stack_chk_fail`
     directly rather than falling through to a normal `leave`/`ret`) while staying comfortably
     clear of `archTrapCatchCall`'s frame above it.
  2. `ubsan_catches_signed_overflow` first asserted the caught RIP symbolized to
     `ubsanOverflowTrigger` (the function whose `a + b` actually overflowed), by analogy with
     `stack_protector_detects_smash` and `trap_ud_caught`. It actually resolved to `report+0x0`
     (confirmed with a temporary `klogWrite` debug line, removed after diagnosis). Root cause,
     found via `objdump` on `ubsan.o`: `__stack_chk_fail()` calls `archTrapCatchSoftware()`
     *directly* from the smashed function's own compiler-generated epilogue, so
     `__builtin_return_address(0)` inside it already points into that function -- but UBSan's
     instrumentation calls a specific `__ubsan_handle_*` entry point first, which only then calls
     the shared `report()` helper (`ubsan.c`) as its *last statement*. Since `report()` is
     `_Noreturn` and that call is unreachable-after, clang emits no epilogue following it, so the
     `call`'s return address (computed by the CPU as "the instruction right after the call") lands
     on whatever the linker placed immediately next in `.text` -- which happened to be `report`
     itself. `report()`'s own `__builtin_return_address(0)` is therefore one frame short of the
     original trigger, and exactly *which* address it resolves to is a linker-placement
     coincidence, not something this test should pin down. Fixed by asserting the RIP is any real,
     symbolizable kernel address (`ksymSymbolize` doesn't return its "not found" `"?"` fallback)
     rather than a specific function name -- still proves `TrapCatchInfo` carries genuine captured
     data through the software-trip path, without depending on compiler/linker placement details
     that could shift between clang versions or optimization levels.
