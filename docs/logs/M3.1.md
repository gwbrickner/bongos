## Plan
Design by `architect` (consulted 2026-10-01). Decisions: D-166..D-169. Spec: `docs/specs/acpidump.md`.

Core ideas: a pure, host-tested parser core (`kernel/drivers/acpi/acpi-tables.c`) that reads firmware
memory only through an `AcpiPhysOps` callback; the kernel glue (`acpi.c`) reads through temporary
read-only WB KVA mappings (the HHDM does not map RESERVED memory, where BIOS puts the RSDP and every
table), copies every accepted table into kmalloc/vmalloc memory, and keeps the copies. Only after
`acpiInit` succeeds does `pmmReclaimAcpiMemory()` free the recorded ACPI_RECLAIM ranges.

### 2026-10-01: step 5, test fix after the reclaim landed
- `make test` (qemu-tester) on 6224f1c: bios-1cpu 65/65, uefi-1cpu 63/65. The two failures were the sweeper's ktests
  `acpi_read_phys_matches_copies` and `acpi_reload_matches_and_frees`: on UEFI the RSDP/tables live in ACPI_RECLAIM,
  which D-168 now zeroes and frees, so re-reading firmware bytes is meaningless there. The tests were wrong (they

  byte-for-byte comparison (BIOS, where tables stay RESERVED, still compares everything; a vacuity guard requires a

  leaking any kmalloc/vmalloc object. Logged: `pmm: reclaimed 72 KiB of ACPI_RECLAIM` (UEFI), 0 KiB (BIOS),
  `meminfo: check ... OK` on both, `acpi_reclaimed` PASS on both.
